# 背单词发音「越读越慢」问题交接说明

> 用途：把本问题完整交给外部 AI / 开发者分析。内容基于本仓库真实代码与真实测试输出，
> 未验证的部分都标注了 ⚠️ / ❌。

## 0. 一句话概括

Web Speech API 朗读英文单词时，**会话前几个词约 1 秒出声，之后逐渐变成 2–3 秒**（递增型延迟）。
已定位到「内部朗读队列积压 + 引擎回调丢失/残影」这一组原因并做了 4 项修复，
但**开发环境听不到音频**，需要外部诊断确认是否彻底解决。

## 1. 运行环境

| 项 | 值 |
|---|---|
| 系统 / 浏览器 | Windows 11 + Chrome / Edge（Web Speech API `speechSynthesis`） |
| 应用形态 | 纯静态前端（无构建、无框架、无 npm 依赖），`node serve.js` 起 http://127.0.0.1:8777 |
| 语音来源 | 系统语音（Windows SAPI / 浏览器后端）；另有可选的 Kokoro 人声引擎（默认关闭，与本问题无关） |
| 相关文件 | `js/speech.js`（朗读队列）、`js/views/vocab.js`（背单词卡片）、`js/views/settings.js`（设置与诊断面板）、`js/store.js`（设置项） |

## 2. 现象（用户原话）

- 「单词前几个读音都是正常 1s 左右发声，后面的发声差不多是 2-3s，延迟变长了」
- **递增型**延迟：不是每次都慢，而是**越到后面越慢**
- 无报错、无卡死，音频内容完整播完，只是「出声越来越晚」
- 与听力播放无关：听力点播放后有**故意的约 2 秒起始缓冲**（那是独立的产品需求）

### 3.2 串行队列 `js/speech.js:285` / `js/speech.js:304`

```js
_enqueue(text, o = {}) {
  return new Promise(resolve => {
    this._q = this._q || [];
    // 背单词：最新优先——丢掉队里的旧词请求并 resolve，避免积压导致越读越慢
    if (o.word) {
      const stale = this._q.filter(job => job.o && job.o.word);
      this._q = this._q.filter(job => !(job.o && job.o.word));
      stale.forEach(job => job.resolve(null));
    }
    this._q.push({ text, o, resolve, queuedAt: Date.now(), engineBusyAtQueue: this._engineBusy() });
    this._pump();
  });
},

_pump() {
  if (this._busy) return;              // 串行：一次只播一条
  const job = this._q && this._q[0];
  if (!job) return;
  this._q.shift();
  this._busy = true;
  const u = new SpeechSynthesisUtterance(prof.frontSpace ? ' ' + job.text : job.text);
  u.voice = this.pickVoice(...);
  // ... onend/onerror → done()；done() 里释放 _busy 并继续 _pump()
  const sinceStop = this._stoppedAt ? Date.now() - this._stoppedAt : Infinity;
  const preRoll = Math.max(this.MIN_PREROLL_MS, this.SETTLE_MS - sinceStop); // 30 / 200ms
  setTimeout(() => doSpeak(0), preRoll);
},
```

## 11. 2026-10-12 复查与修复补记

本节记录交接说明写成后的新证据；上文的“主因假设”仍是当时状态，不应读成真实浏览器已验证的结论。

- **确认的代码竞态**：`stop()` 清掉了队列，却没有清掉当前请求的预等待定时器，也没有在浏览器不回调时结算当前 Promise。旧请求可在停止后继续调用 `speechSynthesis.speak()`。迟到的 `onerror/onend` 还会释放新请求的 `_busy` 锁。`_sayCur()` 只查看浏览器的 `speaking/pending`，预等待阶段被误判为空闲；重复自动朗读也会先取消再去重。
- **已修改**：当前请求由独立令牌管理；停止时取消预等待定时器并结算请求；收尾只执行一次，旧回调不能释放新锁；去重后才按应用内部状态决定是否打断。诊断表的 `waitMs` 从真正入队时开始计算，包含队列等待。
- **回归证据**：新用例在旧代码上失败，在修改后通过；覆盖预等待时停止、迟到取消回调、连续快速切换 20 个词只留下最后一个。原有发音检查 17 项通过；全系统 `node tools/check-all.cjs` 为 11 套、129 项通过、失败 0。

## 12. 2026-10-13 补记：Kokoro 停止不结算（发音自检卡在第 15 项）已修复

### 12.1 现象（必现，且失败是静默的）

`node tools/check-speech-options.cjs` 打印 14 项 `PASS` 和一行 DEBUG 后**直接退出，退出码为 0**：
后面 5 项与汇总行都不出现。失败原因不是断言不通过，而是第 15 项 `await playing` 永不返回；
事件循环随即空转，Node 静默退出。**测试"看起来通过"其实只跑了一半**——这类静默截断比 FAIL 更危险。

### 12.2 根因（单一假设，运行时探针已证实）

`js/speech.js` 的 `neural` 对象字面量里 **`stop()` 与 `busy` 各被写了两次**，后定义的覆盖前面的：

- 生效的 `stop()` 只清 `neural._queue` 并 cancel `_active`——而 `say()` 根本不走这条队列路径；
- `say()` 真正的结算函数 `_finish`、音频元素 `_audio`、`playing` 全都不在它的处理范围内；
- 另一个"会暂停音频"的 `stop()` 是**死代码**，从未生效。

因此 §11 的 `stop()` 修复只覆盖了**系统语音**路径，**Kokoro 路径一行都没覆盖到**。

探针 `work/probe-neural-stop.cjs` 实测（模拟 Kokoro 播放中调用 `Speech.stop()`）：

| 观察点 | 修复前 | 修复后 |
|---|---|---|
| `neural.playing` | `true` | `false` |
| `neural._audio` | 仍存在 | 已清空 |
| `audio.paused` | `false`（**停止后音频还在响**） | `true` |
| 调用方 Promise | `HUNG`（300ms 内不结算） | `settled` |
| `onerror` 回调 | `[]`（一次都没有） | `["canceled"]` |

### 12.3 修法

1. `neural.say()` 为**每次请求**建一个 `job`（`cancel` / `finished` / `audio` / `resolve`）；`stop()` 拿到 job 即可结算，**与 `_audio` 是否已创建无关**；
2. 合成期间被 `stop()`：`generate()` 返回后**丢弃结果**，绝不在停止之后突然出声；
3. 被取消时：暂停音频元素 → `playing = false` → 以 `{ error: 'canceled' }` 回调 `onerror` → `Promise` 以 `null` 结算（沿用 canceled 语义）；
4. 删掉被覆盖的重复 `stop()` / `busy` 定义；`Speech.stop()` 里重复调用 `neural.stop()` 合并为一次；
5. 删掉 `el.ended = …`（`ended` 是只读布尔属性、不是事件，这行从未生效）。

## 13. 2026-10-13 续做：② lookahead 预推理、③ 真人词典音频层、④ Edge 在线音色

### 13.1 ② lookahead 预推理缓冲（已实现）

**问题**：Kokoro 在浏览器里合成一句话要几百毫秒到 1 秒。原来「读完一句 → 再合成下一句」，
这段合成时间直接加进句间静默里，听感是「读完一句要等一会儿才出下一句」。

**做法**（`js/speech.js` + `js/views/listening.js`）：

- 合成结果按 `音色|语速|文本` 作键缓存（LRU，上限 16 条）；
- **当前句开口前**就把下一句送进合成（听力 `_playLines` 的 `step()` 里，往后跳过空行、
  用下一句自己的说话人音色）；轮到它时 `_obtain()` 直接复用，句间只剩 `_sentenceGap()` 设计的停顿；
- 预取**只合成、不播放**——预取路径根本不创建 `Audio` 元素，所以停止/切段后不会突然出声；
- 现合成的结果同样入缓存 → 重播同一句 / 同一个词不必再合成；
- 预取失败静默丢弃，真正要播时重新合成并走正常回落；系统语音引擎下预取是零成本空操作。

**证据**：`tools/check-speech-prefetch.cjs`（新增，10 项）——
预取不产生 Audio、复用不二次合成、语速不同必重新合成、失败不影响播放、缓存有上限、被 stop 后不出声、
**合成期间 stop() 调用方立刻结算**（合成本身无法中断，但 await 不允许被拖住）；
听力侧的行为级断言在 `check-listening-exam.cjs`：「本句开口前就预取下一句（跳过空行、用下一句自己的音色）」。

> 顺带发现（**未修**）：neural 路径的语速取自 `o.rate || 1`，并没有读 `profile(true).rate`，
> 所以设置页的「背单词语速」滑块对 Kokoro 不生效（对系统语音生效）。属于既有行为，改动会影响实际听感，留待确认。

| `GET /dictvoice?audio=deserve&type=2` | 200、`audio/mpeg`、10989 字节、258ms、ID3 头 |
| 带 `Origin: http://127.0.0.1:8777` 的 GET | **无 ACAO / 无 ACAC** |
| `OPTIONS` 预检 | **403**，无 ACAO |
| 响应头全集 | `connection, content-length, content-type, date, server, set-cookie`（**无 Cache-Control/ETag/Last-Modified**） |

也就是说：页面 `fetch()` 读不到字节 →「缓存」无法在前端按字面实现；
`<audio src>` 直连能播，但响应既不带头又带 `Set-Cookie`，浏览器基本不缓存，每次播放都走网络。
**已与需求方确认**，选定方案：**由 serve.js 提供同源代理 + 磁盘缓存**。

**做法**：

- `serve.js` 新增 `GET /__dict-audio?w=<word>&type=<1|2>`：
  上游主机写死（`DICT_AUDIO_ORIGIN` 仅供自检覆盖），**绝不接受请求里的 URL**（否则就是把本机变开放代理）；
  `w` 只允许纯英文单词（首字符字母，其余字母/撇号/连字符/空格，≤40 字），`type` 只允许 1/2；
  缓存文件名用 sha1（不参与路径拼接，天然无穿越）；上游响应必须 `audio/*` 且 >200 字节才落盘；
  命中磁盘缓存返回 `X-Dict-Cache: hit` + `Cache-Control: immutable`；上游超时 504、非音频/5xx 502。
- `js/speech.js` 新增 `Speech.dict` 通道：**优先级 真人录音 → Kokoro → 系统语音**；
  取音频预算 800ms（`TIMEOUT_MS`），超时只当次失败（服务端仍会继续取回并写缓存，下次就是本机命中）；
  404/405 判定为「没有代理」（如 file:// 打开）→ 本会话标记不可用并回落，不再每个词白等一次；
  口音 `type=1` 英音 / `type=2` 美音（设置页可选）。
- 默认**关闭**：打开后每个单词都会向第三方发起查询（会把用户正在背的词发出去），设置页写明这一点。
- 停止语义与 ① 完全一致：**job 在取音频之前就建好**，所以「取音频期间 stop()」也立刻结算、
  不回落、不再出声。

**证据**：`tools/check-dict-audio.cjs`（新增，14 项）。其中 6 项**真实起 `serve.js` + 本地假上游**，
不依赖外网：首取 miss→上游 1 次、二次 hit→不再打扰上游、英音/美音分开缓存、
非法单词与穿越尝试一律 400 且不打上游、上游超时 504 且不留坏缓存、非音频/5xx 502 且不把错误页当音频存。

### 13.4 ④ 期间修掉的一个真实缺陷（同文件同函数，不得不一起改）

`_speakSystem()` 补加载分支原来写的是：

```js
.sort((a, b) => voiceScore(b) - self.voiceScore(a));
```

`voiceScore` 是 `Speech` 的方法，**裸写成 `voiceScore(...)` 直接 `ReferenceError`**；
`self` 又在本函数更后面才声明（TDZ），两处引用都不成立。
数组只有 1 个元素时 `sort` 不调用比较器，所以自检（模拟环境只给 1 个音色）一直没暴露它；
真实机器有几十个英语音色，一旦走到这条分支就抛错。
变异探针 `work/probe-tdz-voicescore.cjs` 已复现旧写法抛错、当前写法正常朗读。

## 14. 2026-10-13 续做：听力为什么还是「人机声」——人声引擎加载源修复

### 14.1 先分清功能边界（这不是 bug）

- **单词**：走 ③ 真人词典录音（有道 dictvoice）→ 真人声，所以"单词没问题了"。
- **听力**：整句朗读**没有**真人录音来源（词典接口只有单词），只能由引擎合成。
  系统引擎在本机的可用音色全是老式 SAPI5 → 必然是机器声。
- 也就是说：想让**听力**变成人声，只有两条路——Kokoro 人声引擎，或 Edge 的云端自然音色。

### 14.2 本机实测：系统音色本来就不可能好听

注册表枚举本机英语语音包：

| 来源 | 实测 |
|---|---|
| `Speech_OneCore\Voices\Tokens` | **Microsoft George / Hazel / Susan**（en-GB，MSTTS_V110 老式合成） |
| `Speech\Voices\Tokens`（含 WOW6432Node） | **Microsoft Hazel Desktop (en-GB)、Microsoft Zira Desktop (en-US)** |
| 含 `Online` / `Natural` 的音色 | **一个都没有** |

浏览器 | 只装了 **Microsoft Edge**（无 Chrome）

所以：系统引擎下无论怎么调，听感都是这几个人机声。

### 14.3 根因：人声引擎的加载链路在本机网络下拿不到东西

本机 `node fetch` 实测（含底层错误码）：

| 目标 | 结果 |
|---|---|
| `cdn.jsdelivr.net` | ❌ `ECONNRESET`（133ms） |
| `huggingface.co` | ❌ `UND_ERR_CONNECT_TIMEOUT`（10s 黑洞） |
| `fastly.jsdelivr.net` | ✅ 200（1590ms） |
| `gcore.jsdelivr.net` | ✅ 200（1793ms） |
| `unpkg.com` | ✅ 200（700ms，但产物用裸模块名，浏览器无法直接用） |
| `hf-mirror.com` | ✅ 200（模型 q8 88.1MB 可取） |
| `dict.youdao.com` | ✅ 200（218ms，所以单词那条路是通的） |

**关键**：光把 `import()` 的 URL 换成可用 CDN 还不够——`transformers` 内部还有两处**写死的默认地址**，
本机都会挂，且失败是"悄悄回落系统语音"，看起来就像什么都没发生：

```
env.remoteHost                   = https://huggingface.co/                                  ← 取模型
env.backends.onnx.wasm.wasmPaths = https://cdn.jsdelivr.net/npm/@huggingface/transformers@<ver>/dist/  ← 取 wasm
```

（从 fastly 上的 `transformers@3.5.1/+esm` 产物里直接读出来的字面量。）

### 14.4 修法（`js/speech.js` 的 `neural`）

1. **CDN 候选表**按顺序试：`fastly` → `gcore` → `cdn`（原地址留作兜底）；
   实测 kokoro 的 `+esm` 内部依赖是**相对路径**（`/npm/@huggingface/transformers@3.5.1/+esm`、`/npm/phonemizer@1.2.1/+esm`），
   所以换基址即整图同源可通（phonemizer 1.35MB 实测 200、无更深依赖）。
2. **模型源候选表**：`hf-mirror.com` → `huggingface.co`，先用 4 秒预算 HEAD 探 `config.json`；
   第一项通就直接用，**根本不去碰被墙的 HF**（省掉 10 秒白等）。
3. **覆盖 transformers 的两处默认地址**：同一基址 import 一次 `transformers` 拿到 `env`（浏览器按绝对 URL 复用模块实例，
   所以 kokoro 内部 import 的是同一个 `env`），设 `env.remoteHost = <模型源>/`、`env.backends.onnx.wasm.wasmPaths = <CDN>/…/dist/`。
4. 失败时把**每个源的失败原因与底层错误码**一起写进 `error`，不再吞成一句"加载失败"。
5. 设置页新增 **「检测下载源」**：与 `load()` 同一份候选表，逐条给 ✓/✗ 与结论，
   让用户在等 88MB 之前就知道这次能不能成。
6. 顺带补上 **男声音色 UI**：听力里 `gender==='male'` 的行一直走 `ttsVoiceMale`，而它此前**没有任何界面**，
   等于被写死成 `am_fenrir`；对以英式男声为主的四六级音源来说这是真缺口（想贴近考试就选 `bm_george`）。

### 14.5 顺带修掉：云端音色的起音预算与"悄悄退回机器声"

`Microsoft * Online (Natural)` 是**联网合成**：首次起音要等网络往返 + 云端合成，原来的 2.5 秒预算经常不够。
更糟的是 no-start 重试会把 `voice` 置空（"交给浏览器默认音色"）——
对云端音色来说这等于**把用户选的音色吞掉、掉回机器声**，现象正是"开了自然音色还是人机声"。

现在：云端音色单独给 `CLOUD_START_TIMEOUT_MS = 9000`，重试**保留原音色**；本地音色行为完全不变（仍是 2.5 秒 + 默认音色重试）；
云端音色最终起不来时给出的提示也改成"需要联网合成"，不再让用户去装语音包。

### 15.2 两条候选路径的实测结论（都做了，都不采用）

**A. 有道 dictvoice 读整句 —— 不可行（但原因在 2026-10-14 被更正）**

> ⚠️ **更正**：本节最初把失败归因为"字符集/长度不支持"。对照实验推翻了这个结论：
> 静默 30 秒后再打**两个已知良好用例**（`deserve`、`Hello world.`）**都恢复 200**；
> 而按 5 秒间隔连打 10 条只成功第 1 条（含之前成功过的简单短句）。
> 即：这是**配额型限流**（`{"msg":"returned null audio"}` 只是限流时的统一应答），
> 下面那张表是在被限流状态下测出来的，**不可作为"支持哪些字符"的依据**。
> 结论本身不变、但理由不同：一次听力要 10–20 条请求，配额撑不住 → 不能做听力引擎。

错误响应体是 `{"status":500,"msg":"returned null audio"}`（限流与不支持时是同一个应答，不能据此区分）。
当时（已限流状态下）测得的表如下，**仅作记录，勿据此判字符支持范围**：

| 输入 | 结果 |
|---|---|
| `Hello world.` / `Hello, world.` / `What do you think?` / `It's fine.` / `What a day!` | ✅ 200 |
| `Hello; world.`（分号）、`A well-known fact.`（连字符）、`He said "yes".`（引号）、`A short test (really).`（括号）、`It costs 25 dollars.`（数字）、`Here is the point: it works.`（冒号） | ❌ 500 |
| 任何 100 字以上的句子 | ❌ 500 |

四六级听力原文几乎必然含数字/连字符/引号 → **覆盖率不够，做不了整句**。

**B. Edge「大声朗读」的 Azure 神经语音（WebSocket）—— 用不了（已停手）**

| 尝试 | 结果 |
|---|---|
| 内置 `WebSocket`（浏览器 API，无法自定义 `Origin`/`User-Agent`） | ✗ 握手失败 |
| 裸 HTTPS 升级（无 Origin/UA） | ✗ 403 |
| 裸升级 + Origin/UA（edge-tts 的标准头） | ✗ 403 |
| GEC 参数 + 版本号的 5 种摆放组合（含头部放法、纯 Chrome UA） | ✗ 全部 403 |

主机可达（普通 GET 返回 400，走东京边缘节点），所以是服务端拒绝该访问形态。
按"失败两次以上就质疑方案"的纪律**停止逆向**：不继续猜微软私有接口。

## 17. 2026-10-14 续：听力"有时还是人机声"的三处根因（已修）

用户报告："听力有时仍用人机声"，并给出两条怀疑：**cloudOff 自愈把云端音色关掉了**、
**没有说话人标注的篇目走了「统一音色」**。逐条查证结果如下（都不是猜测，都有代码位置与自检）：

### 17.1 自愈原来是一次性的（confirm 用户怀疑①）

`cloudOff` 置真后**整会话不再恢复**：`_usable()` 一直返回 false，界面上也没有任何入口能打开它
（设置页「🩺 发音环境诊断」只显示"已自愈关闭"，只能刷新页面）。于是"偶尔一次网络抖动"
会把之后每一句都变成机器声。

**修法**：改成**带冷却的软关闭** —— `CLOUD_RETRY_MS = 60000`，冷却期内用本地音色，
冷却到期自动再试云端；云端成功一次即清零失败计数并解除。设置页新增
**「重新启用云端音色」**（`Speech.resetCloud()`）可立刻重试，`voiceReport()` 会写明
"使用中 / 已自愈关闭（N 秒后自动再试）"。

### 17.2 只认 no-start，导致"起音了却没声"永远不自愈（对应用户给的 38ms 线索）

旧代码只在 `no-start` 时记账。而用户实测的诊断数据是"**起音仅 38ms**"——也就是
**onstart 来了**（38ms 对联网合成来说不可能真的开口），这类失败形态有两种：

| 形态 | 旧行为 | 现行为 |
|---|---|---|
| onstart 后紧接着 onend（听感=没声） | 记为 `end`，算成功，不提示不自愈 | 记为 `no-audio`：朗读时长 < max(150ms, 20ms×字符数) 即判定"起了个头没声" |
| onstart 后再无 onend（回调丢失） | 看门狗 `no-end` 收尾，但**不记账** | `no-end` 同样计入云端失败 |

另外：看门狗原来要等"起音预算"（云端 9 秒）到点才去装第二个定时器；现在 **onstart 一到就换哨**，
"读完没有"的判定不再白等 9 秒。**本地音色不参与这套记账**（本地读得短是正常的），
所以不会误伤系统语音。

### 17.3 "看不出这一句用的是哪个音色"

诊断表原来只有毫秒。现在：

- 听力页「🔍 发音诊断」新增**音色列**：音色名 + **云端/本地**标签，"no-audio" 也会显示在结束原因里；
- 设置页「🩺 发音环境诊断」新增两行：**云端音色状态**（使用中 / 已自愈关闭·几秒后重试）、
  **听力将使用：女声=… / 男声=… / 统一（无说话人标注时）=…**，每个都标注云端或"本地·机器声"；
- 若下拉里**显式选了本地音色**，诊断直接给出 ⚠ 说明：那些句子必然是人机声
  （显式选择优先于"自动优先云端"），把该项改回「自动」即恢复。

> 这一条正是用户怀疑②的机制：听力里带说话人标注的行用 女声/男声 设置，
> **没有说话人标注的行才用「统一音色」**。三个下拉只要有一个被显式选成旧式本地音色
> （早期调试很容易留下这种值），对应的那部分材料就一定是机器声——现象正好是"有时"。

### 17.6 2026-10-14 续：单句听力"还是人机声"——先让它看得见，再一键改回去
