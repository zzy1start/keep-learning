# 第二十二轮：阅读筛选导航 + 单词发音 + 重复背词修复 + 全系统检验报告

本轮四件事：①阅读练习改成按类型/年份/篇章筛选式导航；②单词发音压到 ~1s 且不吞音；
③修掉背单词时同一个词连着背；④改完全系统检验并出报告。

## 一、四项任务：根因 → 改动 → 证据

### 1. 阅读：按类型 / 年份 / 篇章筛选着看

**先说事实**：类型 / 年份 / 场次 / 篇章四个筛选下拉框本来就有（就是截图里那一排），
所以问题不在“没有筛选”，而在两点：

| 问题 | 根因 | 处理 |
|---|---|---|
| 换篇只能开下拉框挑，10 篇要滚动找；顶部只有“篇 10 / 10”这个数字，看不出在哪篇 | 缺少把筛选结果直接铺开的地方 | 新增**筛选结果条**：当前筛选条件下的篇目列成可点条目，点一下即切；另配「上一篇 / 下一篇」，只在当前筛选结果内前后走 |
| AI 生成新文章后跳到别的篇目（带着筛选条件时更明显） | `this.pi = Dict.content.reading.passages.indexOf(p)` —— 用的是**全量数组**下标，而渲染用的是**筛选后**列表下标，筛选越严越对不上，越界还会被归零成第 1 篇 | 改为把筛选条件指向新文章本身（`no: 'id:' + p.id`），下标恒为 0 |

证据：`node tools/check-reading-nav.cjs` → **6 项全过**（条目数量、选中态、首尾禁用、切篇清状态、越界钳制、旧写法已删除）。

### 2. 单词发音：太长 + 吞掉首音节

**两个独立原因，都实测到代码层**：

| 现象 | 根因 | 处理 |
|---|---|---|
| 前面的音节不发声（长单词明显） | `_sayCur` 先 `Speech.stop()`（内部是 `speechSynthesis.cancel()`）紧接着 speak，中间只等 60ms。引擎还在拆上一句时新请求的开头会被截断——这是 Chrome + Windows SAPI 的已知行为 | 记录 cancel 时刻，**间隔不足 240ms 就先等引擎安静**再起音；另加前导空格与一次性静音预热 |
| 一个词要读 1.5–2 秒 | 单词固定 `rate: .85`（句子语速那套参数被用在单词上） | 新增 `Speech.speakWord()`：默认 **1.0** 语速，且**跳过句子语调**（不再给 why/what 这种词加疑问升调） |

顺带把“实测耗时”变成可查的数：`Speech.lastMs` 记录每次朗读实际毫秒数，
设置页新增 **「试听单词并计时」**（读 `interdisciplinary` 并显示 ms，目标 ≈1000ms）。

证据：`node tools/check-speech-options.cjs` → **7 项全过**（单词语速=1.0、疑问词不升调、句子路径不变、cancel 后等待 ≥150ms、记录 lastMs、预热只做一次、stop 清队列）。

> **局限（重要）**：这个环境没有扬声器，我**听不到**合成音频，所以只能说“代码路径与参数已按要求改好”，
> 不能说“我确认过音质了”。请点设置页的「试听单词并计时」核对毫秒数，并人工确认首音节完整。
> 若你的系统音色本身起音慢，可在设置里换「神经网络音色」（如 Aria/Jenny Neural）再试；
> 若仍不满意，下一步可考虑引入开源 TTS（eSpeak-NG WASM 体积小但音质机械；Piper 音质好但每种音色 20–60MB，与离线站点体积有冲突）——需要你先确认能接受体积代价。

### 3. 背单词重复出词（连着背同一个词）

**根因在数据层，不在队列算法**：词书由多个分组文件拼成，同一个拼写在多个文件里各出现一次。

| 词书 | 原始条数 | 唯一拼写 | 重复组数 |
|---|---|---|---|
| CET-4 | 7508 | **4544** | 2354 |
| CET-6 | 5651 | **3991** | 1423 |
| SAT | 8885 | **4462** | 大面积重复 |
| 考研 / 托福 | 6357 / 2760 | 无重复 | 0 |

重复条目内容几乎一样（例：`absorb` 出现 3 次，只是释义详略不同）。
不去重时：① 学习队列里同一个词出现两次 → “连着背同一个词”；② 词书容量虚高（按 7508 算进度，实际只有 4544 个词可学）。

**处理（两层）**：
1. `js/dict.js` 装配时按拼写（小写）去重，保留**信息量更大**的词条（释义×3 + 词组×2 + 例句，同条数再比释义字数，保证结果不随加载顺序波动），`total` 改用去重后的真实数量；
2. `js/views/vocab.js` 增加 `_dedupeQueue()` 兜底：所有模式（新词/复习/智能/随机/拼写）以及拼写重排后都过一遍，任何来源的重复都挡掉。

证据：`node tools/check-vocab-queue.cjs` → **9 项全过**（用真实数据文件验证三本有重复的词书、保留更全释义、词频顺序不变、队列去重、复习池与生词池重叠时只出现一次、发音入口走 speakWord）。

**注意**：词书容量显示会变小（CET-4 从 7508 变为 4544），这是去重后的真实可学词数，不是词库缩水。

### 关于「还剩多少延迟」

能确定的是：**我们自己造成的等待已经降到最低**——没有正在播放时，起音间隔是 30ms（自检里有断言）。
如果设置页计时里的「起音」仍占 700ms 以上，那是系统语音引擎（Windows SAPI / Chrome 后端）的启动延迟，
Web Speech API 没有预热接口，也不能把合成结果缓存成音频文件，所以只能换方案：

| 方案 | 起音 | 音质 | 体积 |
|---|---|---|---|
| 换系统音色（设置页「对比音色延迟」逐个试） | 因音色而异，传统 SAPI 音色通常比 Neural 快 | 传统音色机械、Neural 自然 | 0（系统自带） |
| eSpeak-NG（WASM） | 快（本地合成，无引擎握手） | 明显机械 | ~1–2MB |
| Piper（ONNX + WASM） | 首次加载模型慢，之后较快 | 接近真人 | 每种音色 20–60MB |

要不要引入开源引擎、接受多大体积，等你拍板；在你决定之前，我不会擅自往项目里塞几十 MB 的模型。

## 七、第二十五轮：翻译 0 分的真正根源 / 听力与背单词分离 / 人声引擎

### 1. 翻译 AI 评分的根源（你截图里 0 分 + 「参考译文不完整」）

模型自己的评语就点破了：**「本次材料中的『中文原句』仅呈现考试说明，未包含待翻译的中文段落」**。核对真实数据后确认是**字段取值口径不一致**：

| 字段 | 内容 |
|---|---|
| `translationText` | 中文原文（界面显示的就是它） |
| `prompt` | **考试说明**：`Part IV Translation (30 minutes) Directions: ...` |
| `ai.js` 旧取值 | `prompt` 优先于 `translationText` → 把考试说明当原文发给模型 → 模型合理拒绝评分 → 0 分 |

**处理**：新增唯一口径 `TranslateMetric.sourceOf(task)`（`translationText → prompt → title → en/cn`），
AI 评分、导入核验、本地 chrF 评分、界面显示四处全部改用它；新增回归用例直接复现这道题
（`prompt` = 考试说明 / `translationText` = 中文原文），断言发给模型的是正文而不是说明。

### 2. 听力与背单词：两套独立系统

按你的说明：**听力点播放后先缓冲约 2 秒是听力自己的需求**，与背单词无关。因此：

| 项目 | 听力 | 背单词 |
|---|---|---|
| 起始缓冲 | `listenLeadInMs()`，默认 **2 秒**（设置页可调 0–3 秒） | **无缓冲**，点了立刻读 |
| 语速 | `settings.speechRate` | `settings.wordRate`（默认 1.0） |
| 音色 | `settings.speechVoice` | `settings.wordVoice`（可跟随听力） |
| 语调 | 句子做疑问 / 感叹起伏 | 平直，不做句子语调 |
| 防吞音 | 引擎静音预热 | 前导空格 + 预热 |

读音参数统一由 `Speech.profile(isWord)` 取，两套配置互不影响；设置页拆成了「🎧 听力发音」「📖 背单词发音」两块。

背单词卡片的朗读行为按你的描述固定下来：进入卡片自动读；点**不认识 / 认识 / 熟悉 / 词条详情 / 上一个词**都**强制重播**该词（不受自动朗读去重限制）；进入下一个词读下一个词。

## 八、第二十六轮：背单词「越读越慢」（前几个 1 秒、后面 2–3 秒）

### 现象与根因

这是**递增**延迟，不是固定延迟——对应的只能是「队列在积压」，而不是「引擎慢」。逐条查证后确认四个叠加原因：

| # | 根因 | 说明 |
|---|---|---|
| ① | **引擎回调丢失**（主因） | Chrome / Windows SAPI 偶发不触发 `onstart` / `onend`。原来没有兜底，一次丢失就让内部 `_busy` 永远卡在 true，之后的朗读全部排在队列里 → 延迟越滚越长 |
| ② | **引擎侧 pending 残影** | `cancel()` 之后 Chrome 偶尔不立刻清 `pending`，新请求排在残影后面，延迟逐次变长 |
| ③ | **长会话引擎内部队列变慢** | 连续合成几十次后明显变慢（社区已知现象），需要在空闲时清一次 |
| ④ | **`stop()` 不 resolve 队列任务**（自检揪出） | 清队列时把 Promise 丢下不管，`await` 的调用方（如设置页试听）会永远挂住 |

### 处理

| 处理 | 细节 |
|---|---|
| 看门狗 | 开口超时 2.5s → 强制收尾；读完超时按字数（3s + 字数×220ms）→ 强制收尾。`_busy` 再也不会被卡死 |
| 背单词**最新优先** | 连点时排在队里的旧词请求直接丢弃并 resolve（同一个词读两遍没有意义） |
| 残影清理 | 只在引擎报 `pending`（排队未开口）时先 cancel、按防吞音间隔再开口；`speaking` 状态不碰，避免给每个词平白加等待 |
| 空闲清理 | 每 20 次朗读、且队列为空时 cancel 一次（代价为零，不记 `_stoppedAt`） |
| `stop()` 修复 | 清队列时逐个 `resolve(null)`，调用方不再悬挂 |
| **诊断面板** | 设置页「查看发音延迟诊断」列出最近 12 次的「排队等待 / 起音 / 朗读 / 合计 / 结束原因」——排队等待在涨就是积压，起音在涨才是引擎慢，`no-end/no-start` 就是回调丢失（已兜底） |

### 自检

发音套件 13 → **17 项**：新增看门狗（模拟引擎不回调）、最新优先（队列只留最新且旧请求被 resolve）、诊断环、残影清理（有残影要等、无残影 ≤120ms）。全系统 **10 套 / 128 项全过**。

> 若刷新后仍觉得慢，请点设置页「查看发音延迟诊断」，把那张表发我：
> 「排队等待」持续变大 = 还有积压（我继续查）；「起音」变大 = 系统语音引擎本身慢（换音色或开 Kokoro 人声）。

### 关于我听不到音频这件事

音频听感我无法在这个环境验证，所以每处改动都尽量变成**可测量的数**：
设置页「试听单词并计时」「试听句子」「对比音色延迟」会给出「起音 + 朗读 + 合计」的毫秒数。
按本轮改动推算：听力点播放到出声 ≈ 350ms 缓冲 + 引擎起音（自检里断言缓冲 ≤600ms、未打断时起音间隔 ≤120ms）。
如果实测起音仍占 700ms 以上，那就是系统语音引擎的启动延迟，只能换音色或换引擎（方案见第五节末）。
