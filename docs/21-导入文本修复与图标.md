# 第二十一轮：导入原文修复（拆分单词）+ 文档断句库 + 桌面图标排查

## 1. 问题一：导入后原文里的单词被拆散

### 现象（用户截图 + data/content/writing.json 里的真实数据）

```
在中国传统文化中，…一种重要礼也 (  e tiq u e tte )  。赠送礼物不
仅是物质的馈赠，…中 国 人 遵 循 “ 礼尚往来”  ( mutually exchanging
courtesies )  的传统，…
```

同一批导入数据里还有：`真 题 ( 第 三 套 )`、`(烦 躁 )`、`(自 信 的 )`、`an sw ers`、`com pany`。

### 根因

PDF 的文本层按字块排布，`pdf.js` 提取时会把**字距/定位**还原成空格，于是产生三类损坏：

| 类型 | 例子 | 说明 |
|---|---|---|
| 外文单词被空格拆散 | `e tiq u e tte` → `etiquette` | 中文排版里的西文常逐字定位 |
| 汉字之间被插入空格 | `中 国 人` / `真 题` | 两端对齐的拉伸被当成空格 |
| 标点/括号周围空格 | `“ 礼尚往来”` / `( x )` | 同上，落在标点旁 |
| 版面断行混入正文 | `赠送礼物不\n仅是…` | 行末断行不是段落边界 |

原来的导入链路**完全没有这一步**：提取出来的文本直接交给 AI 切分并入库，
于是损坏被原样写进 `data/content/*.json`（导入会回写磁盘，见 importer 的 `_persist`）。

### 修复

新增 `js/text-repair.js`：`TextRepair.fix()` 只修空白，**不替换任何字符**。

| 规则 | 触发条件（防误伤） |
|---|---|
| 拼回拆散的外文单词 | 片段串里 ≥2 个孤立单字母（a/A/I 除外），或拼出来的词确实在词表里 |
| 去掉汉字之间的空格 | 两侧都是汉字，循环处理到稳定 |
| 去掉标点/括号内侧空格 | 括号一律处理；引号只在后接汉字时处理（英文 `“ says` 不动） |
| 接回版面断行 | 上一行**不是**句末标点结尾、下一行不是题号/标题（`46.` / `Passage` / `Section`） |

接入口（一处修复，AI 与规则切分都受益）：`js/importer.js` 的导入流程入口，
在 `_classifyExamType` / `_aiSplit` / `_ruleSplit` 之前；JSON 导入不做修复。

### 词表校验（避免猜词）

没有孤立单字母的损坏（`an sw ers`、`com pany`）只能靠「拼出来是不是真的词」判断。
因此增加了可选词表钩子 `TextRepair.setWordChecker()`：

- 浏览器里用应用自己的词典（`TextRepair.useLoadedDict()`，词典支持屈折还原）
- 数据修补脚本里用 `data/dictionary.min.json`（103 962 词条）

同时要求窗口内**超过一半**碎片本身不是词，并且不从撇号后的片段起拼：
否则会把正常英文吃掉（实测踩到：`or do`→`ordo`、`take up`→`takeup`、
`re fine`→`refine`、`'s an`→`san`、`'s not`→`snot`）。这些反例都已进回归用例。

### 已入库数据的修补

```bash
node tools/repair-content-text.cjs          # 预览（dry-run，默认）
node tools/repair-content-text.cjs --write  # 写入
```

安全保证：每条改动都断言「去掉全部空白后必须完全一致」（证明没动字），
写回前重新解析比对，并保持每个文件原有的缩进风格（单行文件仍单行）。

结果：`reading.json` 17 处、`writing.json` 8 处、`writing-kaoyan.json` 2 处（分两次写入），
`listening*.json` 无需修复。修复后原文变成：

```
在中国传统文化中，亲朋好友之间互赠礼物是人际交往的一种重要礼也(etiquette)。赠送礼物不仅是物质的馈赠，…
中国人遵循“礼尚往来” (mutually exchanging courtesies)的传统，…
```

### 遗留：字符级错误规则修不了

`礼也` 应为 `礼仪`——这是 PDF 文本层取错字，**不是空格问题**，规则无法安全地猜。
处理方式：`AI.verifyTranslationImport()` 新增 `textIssues` 字段（提示错字/乱码，
但**不阻断**导入），翻译页对已核验题目显示「原文疑似错字 N 处」标签（悬停看详情）。
这样这类问题会显式暴露，而不是看起来一切正常。

**取舍**：本项目是离线静态站点（无 Python、无构建、无后端），能落地的是**纯 JS 的 sbd**。
Python/ML 方案（unstructured / MinerU / marker / pdfplumber）都需要 Python 与模型权重，
与「双击即用」的产品前提冲突，因此只下载并接入 sbd。

### 下载与接入

  commit `6eb72541591136da12e134872dce46ad9c8e76e8`，MIT

## 3. 问题二：桌面图标为什么不见了

### 排查证据（本机实测）

| 检查项 | 结果 |
|---|---|
| 桌面快捷方式 | `Keep Learning.lnk`（2697 字节）存在 |
| 快捷方式 IconLocation | `…\english-app\assets\english-app.ico,0`（路径存在且正确） |
| 快捷方式目标 | `…\node.exe` + `serve.js 8777 --open`（与安装脚本一致） |
| 图标文件 | 87 585 字节，ICONDIR 合法，7 档尺寸（16/24/32/48/64/128/256），每张数据都在文件范围内 |

**结论：文件层面没有问题**（脚本、.ico、.lnk 字段都正确），
剩下的原因是 **Windows 图标缓存没有刷新**——Explorer 在缓存失效/图标被替换后
会回落到「白色文档 + 箭头」的默认快捷方式图标，看起来就是「图标没了」。

### 修复方式

双击应用目录下的 **「修复图标.bat」**：① 校验图标文件（`tools/check-icon.cjs`）
→ ② 清理图标缓存并重启 Explorer → ③ 重新生成桌面快捷方式。
若仍不显示，按提示在桌面按 F5，或注销一次再登录。

另外把「图标文件是否可用」纳入自动检查（`tools/make-lnk.js` 的 `verifyIco()`）：
图标结构损坏时**在创建快捷方式前就报错**，不会再默默生成一个显示默认图标的快捷方式。
